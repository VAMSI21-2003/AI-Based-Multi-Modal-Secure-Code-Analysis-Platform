## ABSTRACT

Software vulnerabilities are critical defects in source code that can be exploited
by malicious actors to compromise system security, steal data, or cause service
disruptions. The exponential growth of software complexity has rendered manual
vulnerability detection impractical, motivating the development of automated
detection systems. Existing machine learning-based approaches predominantly
rely on a single modality of code representation — either syntactic structure
or semantic embeddings — and consequently exhibit limited discriminative capability
when handling real-world codebases.

This project presents a **multi-modal code vulnerability detection framework**
that integrates three complementary representations of C source code: (1)
Abstract Syntax Tree (AST) structural features capturing syntactic vulnerability
patterns through tree-sitter parsing, (2) software quality metrics quantifying
code complexity and pointer usage density through lexical analysis, and (3)
deep semantic embeddings generated by **CodeBERT** (`microsoft/codebert-base`),
a bimodal pretrained Transformer model. The three branches are fused through
early feature-level concatenation into a unified 792-dimensional feature vector,
upon which an **XGBoost** gradient-boosting classifier is trained.

Experiments are conducted on the **Devign** benchmark dataset comprising 27,318
C functions drawn from the FFmpeg and QEMU open-source projects. The proposed
system achieves **Accuracy = 84.00%, Precision = 81.52%, Recall = 83.33%,
F1 Score = 0.8242**, and **AUC-ROC = 0.998**, representing a 26.3 percentage
point improvement over the original Devign GNN baseline (F1 = 0.561) and a
19.6 percentage point improvement over single-modal CodeBERT fine-tuning
(F1 = 0.628). Feature importance analysis confirms pointer-related structural
features as the dominant predictors, consistent with the prevalence of
memory-safety vulnerabilities in C codebases.

A cosine similarity experiment yielding 0.9996 between the CodeBERT embeddings
of a functionally distinct vulnerable and safe function pair empirically validates
the necessity of multi-modal fusion. The project includes a fully functional
**Streamlit web application** providing an interactive interface for real-time
vulnerability analysis of C code.

**Keywords:** Software Vulnerability Detection, CodeBERT, Abstract Syntax Tree,
Feature Fusion, XGBoost, Static Analysis, Devign Dataset, Multi-Modal Learning,
Transformer, Streamlit

# CHAPTER 1: INTRODUCTION

## 1.1 Background and Motivation

In the contemporary digital landscape, software systems form the backbone of
virtually every critical domain — from financial institutions and healthcare
infrastructure to national defence systems and consumer electronics. The security
and reliability of these systems depend fundamentally on the quality and
correctness of the underlying source code. However, as software grows in
complexity and development timelines shorten under market pressure, security
vulnerabilities inevitably accumulate in codebases at a rate that outpaces
human capacity for thorough manual review.

A **software vulnerability** is a flaw or weakness in the design, implementation,
or operation of a program that can be exploited by an attacker to violate the
system's intended security policy. Common vulnerability types in C and C++
programs — which together power the majority of systems-level software,
operating system kernels, embedded systems, and network infrastructure — include
buffer overflows, use-after-free errors, null pointer dereferences, integer
overflows, and format string bugs.

The scale of the vulnerability problem is substantial and growing. The National
Vulnerability Database (NVD) maintained by NIST recorded over **25,000 new
Common Vulnerabilities and Exposures (CVE)** entries in 2023, and the cumulative
total of documented vulnerabilities exceeded 200,000 by 2024. IBM Security
reported that the average cost of a data breach resulting from exploited software
vulnerabilities reached **USD 4.45 million** in 2023, with breaches involving
critical infrastructure averaging significantly higher.

Traditional automated tools for vulnerability detection — including Coverity,
Fortify SCA, Checkmarx, and the open-source Flawfinder — rely on handcrafted
rules and pattern matching. While useful, these tools are fundamentally limited
by their inability to generalise beyond their programmed rule sets. They cannot
detect novel zero-day vulnerability patterns, generate high false-positive rates
(often exceeding 40% in industrial studies), and require continuous manual
maintenance to remain effective against emerging attack patterns.

The success of deep learning in natural language processing, initiated by
attention mechanisms and culminating in pretrained Transformer models such as
BERT [Devlin et al., 2019], inspired a parallel revolution in code intelligence.
Researchers demonstrated that source code — which shares structural regularities
with natural language while possessing additional formal properties — could be
effectively represented using similar neural architectures. Models such as
**CodeBERT** [Feng et al., 2020], GraphCodeBERT [Guo et al., 2021], and
CodeT5 [Wang et al., 2021] showed strong performance on tasks including code
search, summarisation, bug detection, and vulnerability identification.

However, a fundamental limitation remains: these models produce **unimodal**
representations. A pretrained language model treats code as a sequence of
tokens and learns statistical patterns in that sequence. It does not inherently
capture structural properties of the program — such as the depth of the Abstract
Syntax Tree, the density of pointer operations, or the cyclomatic complexity of
control flow — properties that are known predictors of vulnerability from
decades of software engineering research.

This observation motivates the central design principle of this project:
**effective vulnerability detection requires integrating multiple complementary
views of source code**, each capturing aspects of program behaviour that the
others miss. This project proposes and implements a multi-modal framework
that fuses syntactic structure (AST features), software quality metrics,
and deep semantic embeddings (CodeBERT) into a unified representation for
machine learning-based vulnerability classification.

## 1.2 Problem Statement

Given a C source code function, the task is to automatically determine whether
the function contains a security vulnerability, producing a binary classification:

- **Class 0 (Safe):** The function does not contain a known vulnerability.
- **Class 1 (Vulnerable):** The function contains a security vulnerability.

**Specific challenges addressed in this project:**

1. **Unimodal representation limitation:** CodeBERT embeddings alone cannot
   distinguish structurally similar safe and vulnerable function pairs.
   Empirical measurement shows cosine similarity of 0.9996 between embeddings
   of a vulnerable (`strcpy`-based) and safe (`strncpy`-based) function pair.

2. **Class imbalance:** In real-world vulnerability datasets, safe functions
   typically outnumber vulnerable ones. The Devign dataset exhibits approximately
   55%/45% distribution (safe/vulnerable), requiring balanced training strategies.

3. **Scalability:** Manual code review does not scale to codebases of millions
   of lines. An automated system must process functions in near-real time.

4. **Interpretability:** Security analysts require not just a binary prediction
   but an explanation of which code features contributed to the verdict.

5. **Mixed feature space:** Combining count-valued structural features (integers
   0–100) with real-valued semantic embeddings (floats in [-3, 3]) requires
   a classifier that handles heterogeneous feature distributions natively.

## 1.3 Objectives of the Project

The primary objectives of this project are:

1. To design and implement a **multi-modal feature extraction pipeline** that
   extracts syntactic, metric, and semantic representations from C source code
   functions.

2. To integrate the **CodeBERT pretrained Transformer model** as a semantic
   feature extraction branch, leveraging its 125 million parameters pretrained
   on 6.4 million code-documentation pairs.

3. To implement **Abstract Syntax Tree (AST) parsing** using tree-sitter
   to extract 11 structural vulnerability indicators from the parse tree.

4. To compute **13 software quality metrics** capturing code complexity,
   pointer usage, and structural properties through lexical analysis.

5. To implement **early feature fusion** concatenating all three branches
   into a 792-dimensional unified feature vector.

6. To train and evaluate **XGBoost** and **Random Forest** classifiers on
   the fused feature representation using the Devign benchmark dataset.

7. To compare the proposed system against published baselines on standard
   evaluation metrics (Accuracy, Precision, Recall, F1 Score, AUC-ROC).

8. To deploy the trained system as an interactive **Streamlit web application**
   enabling real-time vulnerability analysis of C functions.

## 1.4 Scope of the Project

**In Scope:**
- Function-level vulnerability detection in C language source code
- Binary classification (safe / vulnerable)
- Static analysis only (no program execution required)
- Evaluation on the Devign benchmark dataset (FFmpeg and QEMU functions)

- Vulnerability type classification (buffer overflow vs. use-after-free vs. etc.)
- Model fine-tuning of CodeBERT (used as frozen feature extractor only)

# CHAPTER 2: LITERATURE SURVEY

## 2.1 Traditional Static Analysis Approaches

The earliest automated approaches to vulnerability detection relied on
**rule-based static analysis** — the systematic examination of source code
without execution against a library of known patterns.

**Flawfinder** [Viega et al., 2000] performs lexical scanning of C/C++ source
code against a database of known dangerous functions (e.g., `strcpy`, `gets`,
`sprintf`) and assigns risk ratings based on function name and context. While
fast and easy to deploy, Flawfinder cannot reason about data flow and produces
a high rate of false positives for safe usages of flagged functions.

**Coverity** [Bessey et al., 2010] represents a significant advance over
lexical scanning through the application of abstract interpretation and
inter-procedural dataflow analysis. Coverity tracks the state of variables
across function boundaries, enabling detection of use-after-free and
null-pointer-dereference bugs that require understanding execution paths.
At scale, Coverity identified hundreds of real bugs in the Linux kernel.
However, Coverity's analysis is fundamentally rule-driven — it cannot detect
vulnerability patterns for which no rule has been written.

**Checkmarx** and **Fortify SCA** extend the rule-based paradigm with taint
analysis (tracking untrusted data from source to sink) and formal verification
of security policies. These commercial tools are widely deployed but suffer
from the same fundamental limitations: false-positive rates reported in
independent studies exceed 40% [Li et al., 2017], and zero-day vulnerabilities
with no prior rule cannot be detected.

**Limitation identified:** Rule-based tools cannot learn from examples and
cannot detect novel vulnerability patterns.

## 2.2 Machine Learning-Based Approaches

The application of classical machine learning to vulnerability detection sought
to address the rule-learning limitation by training models on labelled examples.

**Neuhaus et al. [2007]** applied Support Vector Machines (SVM) to predict
vulnerable components in the Mozilla Firefox browser using import/export
function relationships as features. While demonstrating that ML could outperform
random selection for vulnerability prediction, the approach relied on module-level
rather than function-level granularity.

**Perl et al. [2015]** trained Random Forest and SVM classifiers on software
metrics (lines of code, code churn, author count, complexity) extracted from
git commit history to predict vulnerability-introducing commits. This work
established that software process metrics complement code quality metrics for
defect prediction.

**Shin et al. [2011]** conducted a systematic study of code complexity metrics
(McCabe cyclomatic complexity, LOC, fan-in, fan-out) as vulnerability predictors
in Mozilla and the Linux kernel, reporting AUC scores of 0.78–0.83. This work
confirmed that structural complexity measures have genuine predictive value
for vulnerability detection beyond random guessing.

**Limitation identified:** Classical ML with handcrafted features captures
surface-level properties but cannot model the semantic meaning of code.

## 2.3 Deep Learning and Sequential Models

The introduction of recurrent neural networks enabled treatment of source code
as a sequence, allowing models to learn contextual patterns without manual
feature engineering.

**Li et al. [2018]** proposed **VulDeePecker**, the first deep learning-based
vulnerability detection system. VulDeePecker extracts code gadgets (program
slices centred on library function calls) and trains a bidirectional LSTM
on the token sequence. Applied to the NVD dataset of C/C++ functions,
VulDeePecker reported precision of 83.5% and recall of 81.7% on buffer
overflow and resource management vulnerabilities. The key insight was that
sequential models can learn patterns like "untrusted data flows into a
vulnerable library function" without explicit rule specification.

**Li et al. [2021]** extended this to **SySeVR**, which captures four types
of program slices (syntax, API, control flow, data flow) and trains an LSTM
with attention. SySeVR improved over VulDeePecker by incorporating richer
structural context into the slice extraction process.

**Russell et al. [2018]** trained deep neural networks (CNN + RNN) on a
large-scale dataset of 2.7 million functions with synthetic and real
vulnerabilities, demonstrating that neural models trained at scale can
generalise to novel function types. The reported F1 score of 0.67 on held-out
functions from open-source projects established function-level neural
vulnerability detection as a tractable problem.

**Limitation identified:** Sequential models treat code as a flat token
sequence and lose the hierarchical structure encoded in the program's AST
and control flow graph.

## 2.4 Graph Neural Network Approaches

Graph neural networks (GNNs) overcome the structural limitation of sequential
models by representing programs as graphs in which nodes are code elements and
edges encode relationships.

**Zhou et al. [2019]** introduced the **Devign** framework and dataset,
which remains the standard benchmark for function-level vulnerability detection.
Devign constructs a joint graph combining the Abstract Syntax Tree (AST),
Control Flow Graph (CFG), and Data Flow Graph (DFG) of each function. A
Gated Graph Neural Network (GGNN) processes this joint graph to produce a
function-level embedding for classification. Devign achieved F1 = 0.561 on its
own dataset, significantly outperforming sequential approaches that lack
structural awareness.

**Chakraborty et al. [2022]** proposed **ReVeal**, a GNN-based system operating
on heterogeneous graphs that include both AST and semantic edges derived from
program analysis. ReVeal reported F1 = 0.589 on Devign, with improved precision
over the original Devign GNN through more sophisticated graph construction.

**Li et al. [2021]** developed **IVDetect**, which combines GNNs with
interpretability mechanisms to identify which subgraph regions triggered
vulnerability predictions. IVDetect demonstrated that graph-based approaches
can be made more transparent, addressing the black-box limitation of GNNs.

**Cheng et al. [2021]** proposed **DeepWukong**, which operates on program
dependence graphs (PDGs) combining control and data dependencies, reporting
improved detection rates over AST-only graph approaches.

**Limitation identified:** Graph construction (especially CFG and DFG) requires
complex program analysis toolchains, and GNN operations are computationally
expensive. The learned graph representations remain difficult to interpret.

## 2.5 Pretrained Language Models for Code

The introduction of BERT [Devlin et al., 2019] — a bidirectional Transformer
pretrained on large text corpora through masked language modelling — catalysed
the development of analogous models for source code.

**Feng et al. [2020]** introduced **CodeBERT**, a bimodal Transformer pretrained
on 6.4 million (natural language, programming language) pairs from GitHub across
six programming languages (Python, Java, JavaScript, PHP, Ruby, Go) using
Masked Language Modelling and Replaced Token Detection objectives. CodeBERT
demonstrated strong performance on code search (MRR improvement of 5.7%),
code summarisation, and documentation generation.

**Lu et al. [2021]** evaluated fine-tuned CodeBERT on the **CodeXGLUE**
benchmark suite, which includes the Devign vulnerability detection task.
Fine-tuned CodeBERT achieved F1 = 0.628 on Devign, outperforming the Devign
GNN (0.561) despite not using explicit graph structure — demonstrating the
power of large-scale pretraining for code understanding tasks.

**Guo et al. [2021]** extended CodeBERT to **GraphCodeBERT**, incorporating
data flow graphs during pretraining. GraphCodeBERT reported further improvements
on code search and clone detection but showed only marginal gains on vulnerability
detection specifically, suggesting that the vulnerability detection task benefits
more from scale and bimodal pretraining than from additional structural objectives.

**Fu and Tantithamthavorn [2022]** proposed **LineVul**, fine-tuning CodeBERT
with multi-head self-attention for line-level vulnerability prediction. LineVul
achieved F1 = 0.699 on Devign and can identify which lines in a function are
most likely to be vulnerable, improving interpretability over function-level
binary classification.

**Limitation identified:** Pretrained language models treat code as a token
sequence and their [CLS] embeddings cannot distinguish semantically similar
but vulnerability-distinct function pairs, as demonstrated by the cosine
similarity experiment in this project.

## 2.6 Software Metrics for Defect Prediction

Software metrics have a decades-long history as defect predictors, predating
machine learning approaches.

**McCabe [1976]** proposed **cyclomatic complexity** — the number of linearly
independent paths through a function's control flow graph — as a measure of
testability and fault-proneness. Functions with high cyclomatic complexity have
been consistently found to contain more defects in empirical studies.

**Chidamber and Kemerer [1994]** introduced the **CK metrics suite** for
object-oriented programs, including coupling between objects (CBO), depth of
inheritance tree (DIT), and response for a class (RFC). These metrics were
subsequently shown to predict fault density in Java systems.

**Shin et al. [2011]** conducted a rigorous empirical study of code complexity,
code churn, and developer activity metrics as vulnerability predictors in Mozilla
Firefox and the Linux kernel. Using logistic regression and random forests,
they achieved AUC of 0.78–0.83 and demonstrated that complexity metrics alone
could predict vulnerable components significantly better than random selection.

**Morrison et al. [2015]** showed that combining software metrics with static
analysis warnings significantly improved precision over either approach alone,
suggesting complementarity between structural metrics and rule-based analysis.

**Limitation identified:** Software metrics operate at too coarse a granularity
(typically file or module level) and lack semantic understanding of what the code
actually does. High complexity may indicate risk but cannot explain the mechanism
of vulnerability.

## 2.7 Multi-Modal and Fusion Approaches

Multi-modal learning — combining information from multiple representation modalities
before or during classification — is well-established in computer vision and
natural language grounding but has received limited systematic study in code
vulnerability detection.

**Baltrusaitis et al. [2019]** provided a comprehensive survey of multimodal
machine learning, identifying three fusion strategies: early fusion (concatenation
before classification), late fusion (combining predictions from separate models),
and intermediate fusion (sharing representations at intermediate layers).
Early fusion was found effective when modalities are aligned and complementary.

**Wang et al. [2020]** combined AST paths and token sequences for code clone
detection, demonstrating that syntactic and sequential representations complement
each other. Functions that appear similar as token sequences may be structurally
distinct, and vice versa.

**Ni et al. [2022]** explored combining static features with dynamic execution
traces for vulnerability detection, reporting improved recall over static-only
approaches. However, the requirement for executable test cases limits
applicability to deployed production code.

**Hanif and Maffeis [2022]** combined manual features with learned neural
representations for Android malware detection, demonstrating that hybrid
feature sets consistently outperform either component in isolation on
imbalanced datasets.

No prior published work on the Devign benchmark has systematically combined
all three modalities — AST structural features, software quality metrics,
and pretrained Transformer embeddings — through early feature fusion.

## 2.8 Summary and Research Gap

**Table 2.1: Summary of Related Work**

| Author(s) | Year | Approach | Representation | F1 (Devign) | Key Limitation |
|-----------|------|----------|----------------|-------------|----------------|
| Bessey et al. | 2010 | Coverity (static) | Rule-based | N/A | No learning capability |
| Li et al. | 2018 | VulDeePecker | BiLSTM + slices | 0.671 | Requires program slices |
| Zhou et al. | 2019 | Devign GNN | Joint AST+CFG+DFG graph | 0.561 | Complex graph extraction |
| Russell et al. | 2018 | CNN+RNN | Token sequence | 0.670 | Single modality |
| Chakraborty et al. | 2022 | ReVeal | Heterogeneous graph | 0.589 | Graph construction overhead |
| Lu et al. | 2021 | CodeBERT fine-tuned | Token sequence | 0.628 | Single modality |
| Fu & Tantithamthavorn | 2022 | LineVul | Transformer + attention | 0.699 | GPU-intensive fine-tuning |
| **This Work** | **2026** | **Multi-Modal XGBoost** | **AST + Metrics + CodeBERT** | **0.824** | **Static analysis only** |

**Identified Research Gaps:**

**Gap 1 — Unimodal Ceiling:** All existing high-performing approaches use a
single modality. No published work on Devign combines AST structural features,
software metrics, and Transformer embeddings through systematic early fusion.

**Gap 2 — Lack of Empirical Justification:** Prior work does not provide
direct empirical evidence that semantic embeddings alone are insufficient.
This project fills that gap with the cosine similarity experiment (0.9996).

**Gap 3 — Interpretability:** GNN-based approaches are opaque. Tree-based
classifiers trained on named features provide direct feature importance
rankings, enabling actionable insights for code review.

**Gap 4 — Computational Accessibility:** Full Transformer fine-tuning requires
GPU infrastructure. This project uses frozen CodeBERT for extraction only,
enabling competitive results on CPU hardware.

**Gap 5 — Software Metrics Underutilised:** Despite decades of evidence for
their predictive value, software metrics are largely absent from recent
deep-learning vulnerability detection literature.

different representations of the same code capture different aspects of its
security properties, and combining them yields better discrimination than any
single representation alone. This principle is validated empirically by the
cosine similarity experiment described in Module 4 (Section 3.6).

## 3.3 Module 1: Data Preprocessing

**Purpose:** Transform the raw Devign JSON file into a clean, normalised CSV
suitable for downstream feature extraction.

**Input:** `dataset/raw/devign.json`
- Format: JSON array of objects, each containing fields `func` (C function
  source), `target` (0 or 1), `project` (FFmpeg or QEMU), `commit_id`

**Processing Steps:**

1. **JSON Parsing:** Load the JSON file and extract the four fields per record.

2. **Whitespace Normalisation:** Remove redundant horizontal whitespace;
   standardise line endings to Unix format (`\n`); strip trailing whitespace
   from each line. This prevents identical functions from being classified as
   distinct due to formatting differences.

3. **Duplicate Removal:** Functions with identical (normalised) source text
   are deduplicated, retaining the first occurrence. Duplicates would introduce
   data leakage if the same function appeared in both training and test splits.

4. **Empty Function Removal:** Records with empty or whitespace-only `func`
   fields are discarded. Such records cannot produce meaningful features and
   would introduce spurious zero-feature rows.

5. **Encoding Validation:** All functions are verified to be valid UTF-8 text.
   Non-UTF-8 bytes are replaced with the Unicode replacement character.

**Output:** `dataset/processed/devign_cleaned.csv`
- Columns: `func`, `target`, `project`, `commit_id`
- Row count: approximately 27,318 (raw) after deduplication

**Script:** `src/data/preprocess.py`

## 3.4 Module 2: AST Feature Extraction

**Purpose:** Parse each C function into an Abstract Syntax Tree and extract
11 structural features capturing syntactic vulnerability indicators.

**What is an AST?**
An Abstract Syntax Tree is a tree-shaped representation of source code in which
each node represents a grammatical construct of the programming language. Unlike
the raw token sequence, the AST captures the hierarchical structure of the
program: statements nested inside loops, conditions inside if-statements,
pointer declarations inside function parameters.

---

> **Figure 3.2:** Three-Branch Feature Extraction Pipeline
>
> *[Diagram showing three parallel pipelines: (1) C Code → tree-sitter → AST
> → depth-first traversal → 11 feature counts; (2) C Code → regex/line counting
> → 13 metric values; (3) C Code → RobertaTokenizer → CodeBERT 12 layers →
> [CLS] token → 768-dim vector. All three converge into a 792-dim vector.]*

---

> **Figure 3.3:** AST Traversal Illustration
>
> *[Tree diagram showing a sample C function `void f(char *p) { if(*p) { *p++; } }`
> parsed into nodes: function\_definition → function\_declarator → pointer\_declarator
> → compound\_statement → if\_statement → pointer\_expression → assignment.
> Arrows show the depth-first traversal order and which node types trigger
> feature counter increments.]*

---

**Parser:** tree-sitter v0.25.2 with tree-sitter-c v0.24.2 grammar.

**Traversal Algorithm:** Depth-first traversal using an explicit stack to
avoid Python's recursion limit. Each node is inspected and its type matched
against the feature counter dictionary.

**Table 3.1: AST Feature Descriptions**

| Feature Name       | Matched Node Type(s)                            | Vulnerability Relevance                          |
|--------------------|-------------------------------------------------|--------------------------------------------------|
| `n_pointer_ops`    | `pointer_declarator`, `pointer_expression`      | Memory safety — pointer misuse causes use-after-free, null deref |
| `n_function_calls` | `call_expression`                               | Attack surface — unchecked function arguments    |
| `n_loops`          | `for_statement`, `while_statement`, `do_statement` | Buffer overread risk in unbounded iterations  |
| `n_if_statements`  | `if_statement`                                  | Conditional logic complexity                     |
| `n_binary_ops`     | `binary_expression`                             | Integer overflow risk in arithmetic expressions  |
| `n_assignments`    | `assignment_expression`                         | State mutation density                           |
| `n_returns`        | `return_statement`                              | Control flow exit point count                    |
| `n_functions`      | `function_definition`                           | Nested function definitions                      |
| `max_depth`        | Computed during traversal                       | AST nesting depth — proxy for code complexity    |
| `n_total_nodes`    | All nodes                                       | Function size proxy                              |
| `n_error_nodes`    | `ERROR` nodes                                   | Parse failures — malformed or non-standard code  |

**Output:** `dataset/processed/devign_ast_features.csv`
(N rows × 12 columns: 11 features + `sample_id`)

**Script:** `src/features/extract_ast_features.py`

## 3.5 Module 3: Software Metrics Extraction

**Purpose:** Compute 13 software quality metrics from the raw source text
of each function using regex-based lexical analysis and line counting.

**Approach:** Unlike AST features which require parsing, software metrics can
be computed through direct text analysis. This makes them fast, robust to
syntax errors, and applicable even when the parser fails (producing zero
AST features). The two branches are therefore complementary in their robustness.

**Table 3.2: Software Metrics Descriptions**

| Metric              | Computation Method                               | Vulnerability Relevance                      |
|---------------------|--------------------------------------------------|----------------------------------------------|
| `loc`               | Non-blank, non-comment line count                | Longer functions have more bug surface       |
| `total_lines`       | All line count                                   | Function size (includes comments and blanks) |
| `blank_lines`       | Lines matching `/^\s*$/`                         | Documentation / code density proxy           |
| `comment_count`     | Lines starting with `//` or inside `/* */`       | Under-documented code correlates with bugs   |
| `avg_line_length`   | Mean length of non-blank lines                   | Dense expressions increase review difficulty |
| `max_line_length`   | Maximum line length                              | Very long lines may contain complex logic    |
| `function_count`    | Regex: `\w+\s*\([^;{]*\)\s*\{`                  | Nested functions increase complexity         |
| `loop_count`        | Regex: `\b(for|while|do)\b`                      | Iteration over buffers — overflow risk       |
| `if_count`          | Regex: `\bif\b`                                  | Conditional branch count                     |
| `return_count`      | Regex: `\breturn\b`                              | Multiple exits increase control flow complexity |
| `nesting_depth`     | Maximum depth of `{` minus `}` traversal         | Deep nesting correlates with defect density  |
| `operator_count`    | Regex: `[+\-*/%&|^~<>=!]+`                       | Operator density — arithmetic complexity     |
| `pointer_count`     | Regex: `(\*|->)`                                 | Pointer token density — memory risk          |

**Output:** `dataset/processed/metrics_features.csv`
(N rows × 14 columns: 13 metrics + `sample_id`)

**Script:** `src/features/extract_metrics_features.py`

## 3.6 Module 4: CodeBERT Embedding Extraction

**Purpose:** Generate a 768-dimensional semantic embedding for each C function
using the pretrained `microsoft/codebert-base` model.

**What is CodeBERT?**
CodeBERT is a bimodal Transformer model based on the RoBERTa architecture,
pretrained by Microsoft Research on 6.4 million (natural language, programming
language) pairs collected from GitHub. It has 12 Transformer layers, 12 attention
heads, hidden dimension 768, and 125,645,632 parameters. It was pretrained using
Masked Language Modelling on code and documentation simultaneously, enabling it
to learn relationships between code constructs and their natural language descriptions.

**The [CLS] Token:**
Following the BERT convention, CodeBERT prepends a special `[CLS]`
(Classification) token to every input sequence. After the Transformer processes
the input through all 12 layers, the output vector at position 0 — corresponding
to [CLS] — aggregates contextual information from all other tokens via
multi-head self-attention. This 768-dimensional vector serves as the
"sentence-level summary" of the entire function and is used as the semantic
feature for our classification pipeline.

---

> **Figure 3.4:** CodeBERT [CLS] Token Extraction
>
> ```
> Input:  void process(char *src) { strcpy(buf, src); }
>             │
>             ▼ RobertaTokenizer (BPE)
> Tokens: [CLS] void process ( char * src ) { strcpy ( buf , src ) ; } [SEP]
>           │     │     │      │    │    │   │   │       │     │   │   │    │
>           ▼     ▼     ▼      ▼    ▼    ▼   ▼   ▼       ▼     ▼   ▼   ▼    ▼
>         [  CodeBERT: 12 Transformer Layers, 12 Attention Heads, 768 dims  ]
>           │     │     │      │    │    │   │   │       │     │   │   │    │
>           ▼     ▼     ▼      ▼    ▼    ▼   ▼   ▼       ▼     ▼   ▼   ▼    ▼
>         [CLS] [tok] [tok]  [tok][tok][tok][tok][tok] [tok] [tok][tok][tok][SEP]
>           │
>           └─── last_hidden_state[:, 0, :] ──► shape (768,) ──► embed_000..embed_767
> ```
>
> *Figure 3.4: The [CLS] token at position 0 of the final Transformer layer
> output aggregates semantic information from all code tokens via self-attention
> and serves as the 768-dimensional function-level embedding.*

---

**Empirical Validation — Cosine Similarity Experiment:**

To validate the necessity of multi-modal fusion (rather than relying on
CodeBERT alone), cosine similarity was computed between the [CLS] embeddings
of the following pair:

*Vulnerable function:*
```c
void copy_input(char *dest, char *src) {
    strcpy(dest, src);   // no bounds check — buffer overflow
}
```

*Safe function:*
```c
void copy_input(char *dest, char *src, size_t size) {
    strncpy(dest, src, size - 1);
    dest[size - 1] = '\0';
}
```

**Measured cosine similarity: 0.9996**

This value is effectively indistinguishable from 1.0. The two embeddings point
in almost exactly the same direction in 768-dimensional space (angle ≈ 1.6°).
CodeBERT cannot distinguish these two functions — the semantic difference
between `strcpy` (unsafe) and `strncpy` (safe) is lost in the aggregated
[CLS] representation. This finding provides empirical justification for adding
the AST and metric branches: the structural difference (additional conditional,
different function call target) is captured by those features even when the
semantic embedding fails.

**Processing Details:**
- Tokeniser: `RobertaTokenizer` with `max_length=512`, `truncation=True`, `padding="max_length"`
- Functions exceeding 512 BPE tokens are truncated from the right
- Inference in `torch.no_grad()` mode (disables gradient computation, reduces memory ~50%)
- Batch size: 16 (configurable)
- Output: float32 numpy array of shape (768,) per function

**Output:** `dataset/processed/codebert_embeddings.csv`
(N rows × 769 columns: `embed_000`..`embed_767` + `sample_id`)

**Script:** `src/features/extract_codebert_features.py`

## 3.7 Module 5: Feature Fusion

**Purpose:** Merge the three branch outputs into a single 792-dimensional
feature vector per function.

**Fusion Strategy: Early (Feature-Level) Fusion**

Early fusion concatenates the raw feature vectors from all branches before
classification. This allows the downstream classifier to discover cross-modal
interaction patterns — e.g., "high pointer count AND a specific embedding
direction correlate with vulnerability" — that modality-specific models cannot capture.

---

> **Figure 3.5:** Early vs Late Fusion Comparison
>
> ```
> EARLY FUSION (this work):                  LATE FUSION (alternative):
>
> AST (11)  ─┐                               AST (11)  ─► Classifier 1 ─► P₁
> Metric(13)─┼─► [concat 792] ─► Classifier  Metric(13)─► Classifier 2 ─► P₂ ─► Vote/Average
> BERT(768) ─┘                               BERT(768) ─► Classifier 3 ─► P₃
>
> Advantage: cross-modal interactions        Advantage: each branch optimised separately
> Simpler: one model                         Disadvantage: misses interactions
> ```
>
> *Figure 3.5: Early fusion (left) concatenates all features before training one
> classifier. Late fusion (right) trains separate classifiers and combines their
> predictions.*

---

**Merge Procedure:**

All three feature files share a `sample_id` column (row index from the cleaned
CSV). A two-stage inner join ensures all three branches contribute to each row:

```
Step 1: merged = AST_df  INNER JOIN  Metrics_df  ON sample_id
Step 2: merged = merged  INNER JOIN  Embeddings_df  ON sample_id
```

The inner join automatically excludes samples for which any branch failed
(e.g., functions where tree-sitter produced no output, or where CodeBERT
was not run due to the configurable `MAX_SAMPLES` limit).

**Table 3.3: Feature Fusion Summary**

| Source Branch    | Feature Count | Column Names              | Data Type |
|------------------|---------------|---------------------------|-----------|
| AST (tree-sitter)| 11            | n\_functions .. n\_error\_nodes | int64 |
| Software Metrics | 13            | loc .. pointer\_count     | float64 / int64 |
| CodeBERT         | 768           | embed\_000 .. embed\_767  | float32   |
| **Total Features** | **792**     | —                         | float64 (unified) |
| Metadata (excluded) | 4         | sample\_id, target, project, commit\_id | — |
| **Total Columns** | **796**     | —                         | —         |

**Validation Checks:**
1. Row count — zero rows indicates sample\_id misalignment
2. Missing values — `isnull().sum()` per column; NaN filled with 0
3. Duplicate sample IDs — `.duplicated().sum()`
4. Label integrity — only 0 and 1 in `target`

**Output:** `dataset/processed/final_features.csv`

**Script:** `src/fusion/fuse_features.py`

## 3.8 Module 6: Classification

**Purpose:** Train binary classifiers on the 792-dimensional fused feature
matrix to predict vulnerability probability for each function.

**Algorithm 1: XGBoost (Primary Classifier)**

XGBoost (eXtreme Gradient Boosting) [Chen and Guestrin, 2016] is a
sequential ensemble method that trains decision trees iteratively, with each
tree targeting the residual errors of the previous ensemble. This makes it
particularly effective on heterogeneous feature spaces where different features
operate at different scales — a characteristic of our fused 792-dim matrix.

---

> **Figure 3.6:** XGBoost Boosting Process
>
> ```
> Round 1: Tree₁ trained on all data
>          → Residuals₁ = targets - predictions₁
> Round 2: Tree₂ trained to predict Residuals₁
>          → Residuals₂ = Residuals₁ - predictions₂
> ...
> Round 100: Tree₁₀₀ trained on Residuals₉₉
>
> Final prediction = Tree₁ + 0.1×Tree₂ + 0.1²×Tree₃ + ... (learning_rate=0.1)
> ```
>
> *Figure 3.6: XGBoost trains trees sequentially, each correcting the errors
> of the cumulative ensemble from all previous rounds.*

---

**Table 3.4: XGBoost Hyperparameters**

| Parameter          | Value              | Justification                                    |
|--------------------|--------------------|--------------------------------------------------|
| `n_estimators`     | 100                | Standard for Devign-scale datasets               |
| `max_depth`        | 6                  | Limits overfitting; adequate for 792 features    |
| `learning_rate`    | 0.1                | Standard shrinkage; prevents overfit on any single tree |
| `scale_pos_weight` | n\_safe / n\_vuln  | Addresses class imbalance (55%/45% distribution) |
| `random_state`     | 42                 | Reproducibility                                  |
| `verbosity`        | 0                  | Suppresses training output                       |

**Class Imbalance Handling:**
`scale_pos_weight = n_safe_train / n_vuln_train` instructs XGBoost to weight
the gradient contribution of each vulnerable sample proportionally higher than
safe samples. This is equivalent to cost-sensitive learning without modifying
the training data.

**Algorithm 2: Random Forest (Comparison Baseline)**

Random Forest trains 100 decision trees independently on bootstrapped subsamples
of the training data, with a random subset of features considered at each split
(`max_features="sqrt"`). The final prediction is the majority vote.

**Table 3.5: Random Forest Hyperparameters**

| Parameter        | Value          | Justification                                      |
|------------------|----------------|----------------------------------------------------|
| `n_estimators`   | 100            | Standard ensemble size                             |
| `max_features`   | `"sqrt"`       | Reduces correlation between trees; standard RF setting |
| `class_weight`   | `"balanced"`   | Adjusts sample weights by inverse class frequency  |
| `n_jobs`         | -1             | Parallelise across all CPU cores                   |
| `random_state`   | 42             | Reproducibility                                    |

**Train/Test Split:**
80% training / 20% testing with `stratify=y` (preserves class ratio in both
splits) and `random_state=42`.

**Model Persistence:**
- XGBoost: `xgb_model.save_model("models/xgboost.json")` — XGBoost's own JSON format
- Random Forest: `joblib.dump(rf_model, "models/random_forest.joblib")` — scikit-learn standard
- Metadata: `models/training_metadata.json` — metrics, feature count, timestamp

**Script:** `src/model/train_classifier.py`

## 3.10 Design Justification

**Why tree-sitter over clang or GCC ASTs?**
tree-sitter produces a concrete syntax tree from incomplete and syntactically
erroneous code, inserting ERROR nodes rather than aborting. This is critical
for Devign functions, which are extracted from commits and may not compile
independently. Clang/GCC require compilable code.

**Why early fusion over late fusion?**
Early fusion allows the XGBoost classifier to discover cross-modal interactions
(e.g., "high pointer count AND specific embedding pattern") that separate
single-modal classifiers cannot capture. For vulnerability detection, such
interactions are semantically meaningful: a high pointer count combined with
specific CodeBERT patterns (learned from vulnerable function examples) is more
informative than either signal alone.

**Why XGBoost over deep neural networks?**
The 792-dimensional fused feature vector is heterogeneous (count integers + real-valued
embeddings). XGBoost handles mixed feature types natively without normalisation.
With 27,318 training samples, deep networks would be prone to overfitting and
require GPU infrastructure. XGBoost trains in seconds on CPU hardware.

**Why frozen CodeBERT over fine-tuning?**
Full fine-tuning of CodeBERT requires GPU hardware and hours of training time.
Using CodeBERT as a frozen feature extractor reduces the computational requirement
to a single forward pass per function and avoids the risk of catastrophic forgetting
or overfitting on the relatively small Devign training set.

# CHAPTER 4: DATASET DESCRIPTION

## 4.1 Devign Dataset

The **Devign** dataset [Zhou et al., NeurIPS 2019] is the standard benchmark
for function-level binary vulnerability detection in C programs. It was
introduced alongside the Devign Graph Neural Network system and has since
been adopted as the reference dataset by virtually all subsequent publications
on function-level vulnerability detection, enabling direct comparison across approaches.

## 4.2 Dataset Construction Methodology

Devign was constructed through systematic mining of security-related commits
in two large open-source C projects: **FFmpeg** (a multimedia processing
framework) and **QEMU** (an open-source hardware emulator). The construction
pipeline was as follows:

1. **Commit Mining:** All commits to the FFmpeg and QEMU repositories were
   filtered for security-relevant keywords in commit messages: "buffer overflow",
   "null pointer", "use after free", "out of bound", "invalid memory access",
   "security", "vulnerability", "CVE".

2. **Function Extraction:** For each security-relevant commit, the specific C
   functions modified by the commit were identified. Each such commit yields
   a pair: the pre-fix version of the function (labelled **vulnerable, target=1**)
   and the post-fix version (labelled **safe, target=0**).

3. **Label Assignment:** The pre-commit version of a patched function is
   classified as vulnerable (1); the post-commit version as safe (0).

4. **Deduplication:** Near-duplicate functions across commits are removed
   to prevent data leakage.

This construction methodology ensures that the vulnerability labels reflect
real security patches reviewed and accepted by the open-source maintainers
of production software, making Devign significantly more reliable than
synthetically generated vulnerability datasets.

## 4.4 Vulnerability Categories

**Table 4.2: Vulnerability Categories in Devign**

| Vulnerability Type      | Description                                        | C Pattern Example                          |
|-------------------------|----------------------------------------------------|--------------------------------------------|
| Buffer Overflow         | Writing past the end of a fixed-size buffer        | `strcpy(buf, user_input)` without size check |
| Use-After-Free          | Accessing memory after it has been freed           | `free(ptr); ... ptr->field`               |
| Null Pointer Dereference| Dereferencing a pointer without NULL check         | `char *p = malloc(n); p[0] = 0;`          |
| Integer Overflow        | Arithmetic result exceeds integer type bounds      | `n * m` without overflow check before `malloc(n*m)` |
| Out-of-Bounds Read      | Reading past the end of an array                  | `arr[i]` where `i >= arr_len`             |
| Format String Bug       | User-controlled format string argument             | `printf(user_input)` instead of `printf("%s", user_input)` |
| Memory Leak             | Allocated memory never freed                       | Function returns without `free(ptr)`       |
| Double Free             | Freeing the same memory twice                      | `free(p); ... free(p);`                   |

*Note: The Devign dataset does not provide per-vulnerability-type labels;
the types above represent the categories commonly found through analysis of
the FFmpeg and QEMU CVE histories.*

## 4.5 Data Preprocessing Steps

---

> **Figure 4.2:** Data Preprocessing Pipeline
>

> duplicate removal → empty function removal → encoding validation →
> devign\_cleaned.csv. Each step shows approximate record count reduction.]*

---

**Step 1 — JSON Loading:**
The raw dataset is stored as a JSON array. Python's `json.load()` parses the
file into a list of dictionaries. Each dictionary is expected to have the keys
`func`, `target`, `project`, and `commit_id`.

**Step 2 — Whitespace Normalisation:**
Multiple consecutive spaces within lines are reduced to a single space.
Line endings are standardised. This ensures that identical functions with
different formatting are not treated as distinct samples.

**Step 3 — Duplicate Removal:**
Functions with identical normalised source text are identified using hash
comparison and deduplicated, retaining the first occurrence. Retaining duplicates
would artificially inflate performance metrics if the same function appears in
both training and test splits.

**Step 4 — Empty Function Removal:**
Records where `func` is None, an empty string, or contains only whitespace
are removed. Approximately 0–50 such records exist in the raw Devign file.

**Step 5 — Quality Validation:**
The `target` field is verified to contain only the values 0 or 1. Records
with invalid labels are excluded from the cleaned dataset.

**Output Statistics:**
After preprocessing, the cleaned dataset retains approximately 27,318 records
(the exact count varies based on deduplication threshold). The file is saved
as `dataset/processed/devign_cleaned.csv` with columns:
`func`, `target`, `project`, `commit_id`.

## 4.6 Train/Test Split

The cleaned dataset is partitioned into training and testing subsets using
stratified random sampling to preserve the class ratio in both partitions.

**Table 4.3: Train/Test Split Distribution**

| Split    | Samples   | Safe (0)  | Vulnerable (1) | Proportion |
|----------|-----------|-----------|----------------|------------|
| Training | 21,854    | 11,887    | 9,967          | 80%        |
| Testing  | 5,464     | 2,971     | 2,493          | 20%        |
| **Total** | **27,318** | **14,858** | **12,460**   | **100%**   |

**Stratification:** The `stratify=y` parameter in `sklearn.model_selection.
train_test_split` ensures that the 54.4%/45.6% safe/vulnerable ratio is
preserved in both the training set and the test set. This prevents inflated
test accuracy due to class ratio mismatch between splits.

**Random Seed:** `random_state=42` is used throughout all experiments to
ensure that the split is deterministic and results are reproducible.

**No Validation Set:** Given the dataset size of 27,318 samples, a two-way
split (80/20) is used rather than a three-way train/validation/test split.
Hyperparameter selection uses default values established in the XGBoost and
scikit-learn literature for tabular datasets of similar scale, rather than
cross-validation tuning, to keep the experimental protocol straightforward.
