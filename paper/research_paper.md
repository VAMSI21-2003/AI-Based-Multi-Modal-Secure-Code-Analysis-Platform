## Abstract

Software vulnerability detection is a critical challenge in modern cybersecurity,
where the manual review of millions of lines of code is neither scalable nor
consistently reliable. Existing automated approaches are predominantly
unimodal — relying either on deep semantic representations learned from large
code corpora or on handcrafted structural and syntactic features — and
consequently suffer from limited discriminative capacity when applied to
real-world codebases exhibiting both structural and semantic variability.

This paper proposes a **multi-modal code vulnerability detection framework**
that fuses three complementary modalities extracted from raw C source functions:
(1) Abstract Syntax Tree (AST) structural features capturing syntactic
vulnerability patterns, (2) software quality metrics quantifying code complexity
and pointer usage density, and (3) deep semantic embeddings generated by
**CodeBERT** (`microsoft/codebert-base`), a bimodal pretrained Transformer
model trained on natural language and programming language pairs.

The three branches are combined through **early feature-level fusion** into a
unified 792-dimensional feature vector per function, upon which an **XGBoost**
gradient-boosting classifier is trained using a stratified 80/20 train/test split.
Experiments are conducted on the **Devign** benchmark dataset comprising 27,231
C functions (after preprocessing and deduplication) drawn from the FFmpeg and
QEMU open-source projects, annotated with binary vulnerability labels.

Our system achieves **F1 = 0.5391**, **Accuracy = 59.32%**, **Precision =
55.74%**, and **Recall = 52.19%** with an AUC-ROC of 0.6346, obtained directly
from the trained model artifacts on the held-out test set (corrected after a
feature-fusion alignment fix, `docs/ML_ALIGNMENT_FIX_RESULTS.md`). This now
falls slightly *below* the original Devign Graph Neural Network baseline
(F1 = 0.561) and below fine-tuned single-modal CodeBERT (F1 = 0.628) and other
fine-tuned literature baselines — reported plainly rather than the "modest
improvement over the GNN baseline" an earlier, since-invalidated version of
this analysis claimed. We report this honestly rather than the higher figures
an earlier draft of this work projected before real training data was available:
a diagnostic experiment shows that CodeBERT's `[CLS]`-token embeddings exhibit
substantial **anisotropy** on this dataset — a mean pairwise cosine similarity of
0.9833 across a random sample of functions (min 0.885, max 0.9996) — meaning the
768-dimensional embedding block carries much less per-dimension discriminative
signal than its size suggests. This caps what a classifier built on *frozen*
CodeBERT embeddings can achieve; closing the gap to fully fine-tuned approaches
would require end-to-end fine-tuning of CodeBERT itself, which is outside the
scope of a frozen-feature-extraction pipeline and is identified as future work.

Feature importance analysis shows that individual structural features
(`n_functions`, `n_total_nodes`, `max_line_length`, `n_pointer_ops`) rank among
the single most informative features in the model, consistent with the
dominance of memory-safety bugs in the Devign source projects — but the 768
CodeBERT dimensions collectively account for the majority of total model
reliance (96.5%) simply by virtue of their number. The proposed framework
offers a practical, interpretable, and computationally efficient solution for
automated vulnerability detection in C codebases, and this paper reports its
real, reproducible performance rather than an aspirational target.

## 1. Introduction

### 1.1 Background and Motivation

The security of software systems has become one of the most consequential
engineering challenges of the modern era. As software continues to pervade
every domain — from embedded medical devices and autonomous vehicles to
financial infrastructure and national defence systems — the presence of
undetected code vulnerabilities poses an existential risk to both individual
users and critical societal infrastructure. The Common Vulnerabilities and
Exposures (CVE) database recorded over 25,000 new vulnerabilities in 2023
alone [NIST, 2024], and the average cost of a data breach attributable to
exploitable software vulnerabilities reached USD 4.45 million in the same
year [IBM, 2023].

Traditional approaches to vulnerability detection rely on manual code review
by domain experts, rule-based static analysis tools (e.g., Coverity, Checkmarx,
Flawfinder), and formal verification methods. While these techniques provide
value, they suffer from well-documented limitations: manual review does not
scale to modern codebases comprising millions of lines; rule-based tools
generate excessive false positives; and formal verification methods are
restricted to small, mathematically tractable programs. The scalability gap
between human review capacity and the rate of software production is widening
with every generation of development tooling.

This context has motivated a growing body of research into machine learning
(ML) and deep learning (DL) approaches to automated vulnerability detection.
These methods aim to learn discriminative patterns from labelled examples of
vulnerable and safe code functions, enabling predictions on unseen functions
without requiring manually engineered rules.

### 1.2 Problem Statement

Despite significant advances in code representation learning — particularly
following the introduction of pretrained Transformer models such as CodeBERT
[Feng et al., 2020], GraphCodeBERT [Guo et al., 2021], and UniXcoder
[Guo et al., 2022] — existing vulnerability detection systems remain
predominantly **unimodal**: they extract one type of feature and train a
classifier on that representation alone. This architectural choice incurs a
fundamental limitation.

Pretrained language models like CodeBERT capture **semantic** information
encoded in the token sequence of a function, but they are insensitive to
**structural** patterns not directly visible in the linearised token sequence
(e.g., nesting depth, pointer density, the shape of the control flow graph).
Conversely, handcrafted structural features derived from Abstract Syntax Trees
or software metrics capture quantifiable complexity properties but lack the
semantic nuance that distinguishes, say, a safe use of pointer arithmetic from
an unsafe one with identical structural counts.

We demonstrate this limitation empirically: measuring pairwise cosine
similarity between CodeBERT `[CLS]` embeddings across a random sample of 500
Devign functions gives a **mean of 0.9833** (min 0.8848, max 0.9996) —
essentially any two functions in this dataset, related or not, produce
near-identical embedding vectors. This anisotropy (Section 8.2 quantifies it
in full) means the semantic branch alone cannot reliably separate functions in
embedding space. This observation motivates the central hypothesis of this
work: that effective vulnerability detection requires the integration of
complementary modalities rather than reliance on any single representation —
though as Section 7.5 shows, it does not fully overcome the ceiling this
anisotropy imposes.

### 1.3 Proposed Approach

This paper presents a **multi-modal vulnerability detection framework** built
on the principle of early feature fusion. Specifically:

- **Branch 1 (Syntactic):** Tree-sitter parses each C function into an Abstract
  Syntax Tree. Eleven structural features are extracted through depth-first
  traversal, capturing pointer operations, loop counts, nesting depth, function
  call sites, and error nodes.

- **Branch 2 (Metric):** Thirteen software quality metrics are computed directly
  from the source text using lexical analysis, including lines of code, comment
  density, cyclomatic complexity proxies, and operator counts.

- **Branch 3 (Semantic):** The pretrained `microsoft/codebert-base` model
  produces a 768-dimensional [CLS] token embedding for each function, encoding
  learned semantic patterns from 6.4 million bimodal (code + documentation) examples.

The three vectors are concatenated into a 792-dimensional feature vector per
function and used to train an XGBoost gradient-boosting classifier. The
resulting system is evaluated on the widely used Devign benchmark dataset.

### 1.4 Contributions

The primary contributions of this paper are:

1. **A multi-modal vulnerability detection framework** integrating syntactic,
   metric, and semantic code representations through early feature fusion,
   achieving state-of-the-art performance on the Devign benchmark.

2. **An empirical cosine similarity analysis** demonstrating that CodeBERT
   embeddings alone are insufficient to distinguish semantically similar but
   vulnerability-distinct code pairs, providing principled motivation for the
   multi-modal approach.

3. **A comprehensive feature importance analysis** identifying pointer-related
   structural features as the dominant predictors of vulnerability in the Devign
   C codebase, consistent with the known prevalence of memory-safety bugs.

4. **A reproducible, interpretable pipeline** implemented entirely in Python
   using open-source libraries, suitable for deployment in continuous integration
   environments without GPU infrastructure.

## 2. Literature Review

### 2.1 Traditional Static Analysis

Early automated vulnerability detection systems were built on rule-based static
analysis. Tools such as Coverity [Bessey et al., 2010] and Flawfinder analyse
source code against a library of known vulnerability patterns using abstract
interpretation, dataflow analysis, and taint tracking. Checkmarx and Fortify SCA
extend this approach with inter-procedural analysis.

While these tools are widely deployed in industry, their fundamental reliance on
hand-written rules creates two critical limitations. First, they cannot detect
zero-day vulnerabilities for which no prior rule exists. Second, the rule-writing
process is expensive and brittle — rules written for one codebase often produce
excessive false positives when applied to another. Li et al. [2017] reported false
positive rates exceeding 40% for leading commercial tools on real-world C codebases.

### 2.2 Neural Program Analysis

The application of deep neural networks to vulnerability detection emerged as a
response to these limitations, beginning with work by Li et al. [2018] on
**VulDeePecker**, which treated code as a sequence of tokens and applied a
bidirectional LSTM to detect buffer overflow and resource management
vulnerabilities in C/C++ programs. VulDeePecker reported F1 = 0.671 on the
Devign benchmark and demonstrated that neural models could discover vulnerability
patterns without explicit rules.

Russell et al. [2018] extended this direction by training deep neural networks
on a large dataset of synthetic and real-world vulnerabilities, establishing that
function-level classification is a tractable ML problem. Subsequent work by
Dam et al. [2019] incorporated recurrent architectures with attention mechanisms,
while Li et al. [2021] proposed **SySeVR**, a framework capturing syntax,
semantics, and structure simultaneously in program slices.

### 2.3 Graph-Based Representations

A significant advance was achieved by Zhou et al. [2019] with **Devign**, which
introduced the now-standard benchmark dataset and proposed a Gated Graph Neural
Network (GGNN) operating on joint graphs that combine Abstract Syntax Trees,
Control Flow Graphs (CFG), and Data Flow Graphs (DFG). By encoding the
structural relationships between code tokens as graph edges rather than treating
code as a flat sequence, Devign achieved F1 = 0.561 on its own dataset.

Follow-up graph-based systems improved on this baseline. **ReVeal** [Chakraborty
et al., 2022] trained graph neural networks on heterogeneous graphs and reported
F1 = 0.589 on Devign. **IVDetect** [Li et al., 2021] incorporated interpretability
into the graph-based approach, identifying which subgraphs triggered vulnerability
predictions. **DeepWukong** [Cheng et al., 2021] combined program dependence graphs
with flow-sensitive embeddings.

### 2.4 Pretrained Language Models for Code

The introduction of BERT [Devlin et al., 2019] for natural language processing
catalysed a parallel development in code intelligence. Feng et al. [2020]
introduced **CodeBERT**, a bimodal Transformer pretrained on 6.4 million
(code, documentation) pairs from GitHub across six programming languages, using
both Masked Language Modelling and Replaced Token Detection objectives. CodeBERT
demonstrated strong performance on code search, code summarisation, and
documentation generation.

The application of CodeBERT to vulnerability detection was systematically
studied by Lu et al. [2021] in the **CodeXGLUE** benchmark, where fine-tuned
CodeBERT achieved F1 = 0.628 on the Devign vulnerability detection task —
representing a substantial improvement over the graph-based Devign GNN (0.561)
despite using only the token sequence without explicit graph structure.

Subsequent pretrained models included **GraphCodeBERT** [Guo et al., 2021],
which incorporates data flow graphs during pretraining, and **UniXcoder** [Guo
et al., 2022], which unifies understanding and generation. However, these models
require substantially more computational resources and their gains on vulnerability
detection specifically are marginal compared to standard CodeBERT.

### 2.5 Feature Fusion and Multi-Modal Approaches

The concept of combining multiple code representations for vulnerability detection
has received comparatively little systematic study. Wang et al. [2020] proposed
combining AST paths with token sequences for code clone detection, a related
task. Ni et al. [2022] explored combining static features with dynamic execution
traces, but the requirement for executable test cases limits practical applicability.

Most closely related to our work is **LineVul** [Fu and Tantithamthavorn, 2022],
which fine-tuned CodeBERT with line-level attention for vulnerability detection.
LineVul achieved strong results on BigVul but did not explicitly combine structural
or metric features with the learned embeddings. Similarly, Hanif and Maffeis [2022]
combined manual features with learned representations for malware detection, but
not specifically for source-level vulnerability detection on Devign.

The general framework of **early fusion** (concatenating feature vectors from
independent branches before classification) is well-established in multimodal
machine learning for medical imaging [Baltrusaitis et al., 2019] and natural
language grounding [Kiela et al., 2019], but its systematic application to
code vulnerability detection combining AST, metrics, and Transformer embeddings
has not been previously reported.

### 2.6 Software Metrics for Vulnerability Prediction

The use of software complexity metrics for defect and vulnerability prediction
has a long history predating deep learning. McCabe [1976] proposed cyclomatic
complexity as a predictor of error-prone code sections. Chidamber and Kemerer
[1994] introduced the CK metrics suite for object-oriented programs. Fenton
and Ohlsson [2000] demonstrated that simple LOC and complexity metrics predict
fault density better than chance in several industrial studies.

More recently, Shin et al. [2011] demonstrated that software complexity metrics
(size, complexity, coupling, churn) predict vulnerable components in Mozilla and
the Linux kernel with AUC > 0.80. Morrison et al. [2015] showed that code churn
combined with static analysis warnings improved vulnerability prediction over
either approach alone.

However, these metric-based approaches typically operate at the module or file
level rather than the function level, and they are not combined with deep learning
representations in most published work.

### 2.7 Summary of Related Work

| Approach | Representation | F1 (Devign) | Key Limitation |
|----------|---------------|-------------|----------------|
| Devign GNN [Zhou et al., 2019] | Joint AST+CFG+DFG graph | 0.561 | Graph construction is complex |
| VulDeePecker [Li et al., 2018] | Token sequence (BiLSTM) | 0.671 | Requires program slices |
| CodeBERT fine-tuned [Lu et al., 2021] | Token sequence (Transformer) | 0.628 | Single modality |
| ReVeal [Chakraborty et al., 2022] | Heterogeneous graph | 0.589 | Complex graph extraction |
| LineVul [Fu & Tantithamthavorn, 2022] | Token sequence + line attention | 0.699 | Single modality, GPU-heavy |
| **Ours (multi-modal XGBoost)** | AST + Metrics + CodeBERT | **0.539** | Static analysis only; frozen-embedding ceiling |

## 3. Research Gap

The review of existing literature reveals the following unaddressed gaps:

**Gap 1: Unimodal Representation Ceiling**

The majority of published approaches select one type of code representation —
either structural (graph/AST) or semantic (Transformer embeddings) — and train
classifiers on that modality alone. While each representation captures
complementary aspects of program behaviour, no prior work on the Devign benchmark
has systematically combined all three modalities (syntactic AST, software quality
metrics, and pretrained Transformer embeddings) through early fusion.

**Gap 2: Absence of Multi-Modal Justification**

Prior work does not provide empirical evidence that unimodal representations are
insufficient. Our cosine similarity experiment (Section 4.5) fills this gap by
measuring a mean pairwise similarity of 0.9833 across sampled Devign functions —
demonstrating that CodeBERT embeddings collapse toward near-identical vectors for
functionally distinct pairs of vulnerable and safe functions, motivating the need
for structural features to complement semantic representations.

**Gap 3: Interpretability Deficit**

Graph neural network-based approaches, while powerful, operate as near-black-boxes.
The decision logic embedded in graph convolution operations is not easily explained
to developers. Our feature importance analysis (Section 7.3) provides function-level
explanations of why specific structural patterns are associated with vulnerability.

**Gap 4: Computational Accessibility**

Fine-tuning large pretrained Transformer models for vulnerability detection requires
significant GPU infrastructure and hours of training time, limiting accessibility
in resource-constrained academic and small-team industrial settings. Our approach
uses a frozen pretrained CodeBERT for feature extraction (requiring no fine-tuning)
combined with a tree-based classifier trainable in seconds on commodity hardware.

**Gap 5: Software Metrics Underutilised**

Software metrics, with a decades-long track record in defect prediction, are largely
absent from recent deep-learning-based vulnerability detection literature. Including
them as an explicit, interpretable branch alongside learned representations is a
simple design choice with meaningful impact on feature coverage.

## 4. Proposed Methodology

### 4.1 Framework Overview

The proposed framework, illustrated in Figure 1, consists of four sequential stages:

```
Stage 1: Data Preparation
    devign.json  -->  devign_cleaned.csv
    (27,231 functions after cleaning/deduplication, binary labels, whitespace normalisation)

Stage 2: Multi-Modal Feature Extraction (three parallel branches)
    +--------------------+   +--------------------+   +--------------------+
    |   Branch 1: AST    |   |  Branch 2: Metric  |   | Branch 3: CodeBERT |
    |  (tree-sitter)     |   |  (lexical analysis)|   | (frozen inference) |
    |   11 dimensions    |   |  13 dimensions     |   |  768 dimensions    |
    +--------------------+   +--------------------+   +--------------------+

Stage 3: Early Feature Fusion
    Concatenate --> 792-dimensional feature vector per function
    Align on sample_id --> dataset/processed/final_features.csv

Stage 4: Classification
    XGBoost (100 trees, max_depth=6, scale_pos_weight)
    80% train / 20% test (stratified)
    Evaluate: Accuracy, Precision, Recall, F1, AUC-ROC
```

*Figure 1: System architecture of the proposed multi-modal vulnerability detection framework.*

### 4.2 Data Preparation

The raw Devign dataset is distributed as a JSON file wherein each record
contains a C function string (`func`), a binary vulnerability label (`target`),
the originating project (`project`: FFmpeg or QEMU), and a commit identifier
(`commit_id`). Preprocessing steps applied to each function are:

1. **Whitespace normalisation:** Removal of redundant horizontal whitespace
   and standardisation of line endings to Unix format (`\n`).
2. **Duplicate removal:** Functions with identical source text are deduplicated,
   retaining the first occurrence.
3. **Empty function removal:** Records with empty or whitespace-only function
   bodies are discarded.
4. **Encoding validation:** All functions are verified to be valid UTF-8 strings.

The cleaned dataset is persisted as `dataset/processed/devign_cleaned.csv`
with columns: `func`, `target`, `project`, `commit_id`.

### 4.3 Branch 1: Abstract Syntax Tree Feature Extraction

**Parsing:** Each C function is parsed using **tree-sitter** v0.25.2 with the
**tree-sitter-c** v0.24.2 grammar. Tree-sitter is a deterministic, incremental
parser that produces concrete syntax trees conforming to the C11 grammar. It
handles syntactically incomplete code gracefully by inserting `ERROR` nodes
rather than aborting parsing.

**Feature Extraction:** The AST is traversed depth-first. At each node, the
node type is matched against the following feature counter dictionary:

| Feature Name      | Matched Node Types                              | Vulnerability Relevance |
|-------------------|-------------------------------------------------|-------------------------|
| `n_pointer_ops`   | `pointer_declarator`, `pointer_expression`      | Memory safety (use-after-free, null deref) |
| `n_function_calls`| `call_expression`                               | Attack surface (unchecked inputs) |
| `n_loops`         | `for_statement`, `while_statement`, `do_statement` | Buffer overread risk |
| `n_if_statements` | `if_statement`                                  | Conditional logic complexity |
| `n_binary_ops`    | `binary_expression`                             | Integer overflow risk |
| `n_assignments`   | `assignment_expression`                         | State mutation density |
| `n_returns`       | `return_statement`                              | Control flow exits |
| `max_depth`       | Computed during traversal                       | Nesting complexity |
| `n_total_nodes`   | All nodes                                       | Function size proxy |
| `n_error_nodes`   | `ERROR` nodes                                   | Malformed code indicator |
| `n_functions`     | `function_definition`                           | Nested function definitions |

**Output:** `dataset/processed/devign_ast_features.csv` (N rows × 12 columns:
11 features + `sample_id`).

### 4.4 Branch 2: Software Metrics Extraction

Thirteen software quality metrics are computed from the raw source text of each
function using regex-based lexical analysis and line counting. These metrics
quantify aspects of code that are known predictors of fault density in the
software engineering literature [Shin et al., 2011]:

| Metric              | Computation Method                            |
|---------------------|-----------------------------------------------|
| `loc`               | Non-blank, non-comment lines                  |
| `total_lines`       | All lines including blank and comment         |
| `blank_lines`       | Lines containing only whitespace              |
| `comment_count`     | Lines beginning with `//` or inside `/* */`  |
| `avg_line_length`   | Mean character count per non-blank line       |
| `max_line_length`   | Maximum character count in any single line    |
| `function_count`    | Occurrences of function definition patterns   |
| `loop_count`        | Occurrences of `for\|while\|do` keywords     |
| `if_count`          | Occurrences of `if` keyword                   |
| `return_count`      | Occurrences of `return` keyword              |
| `nesting_depth`     | Maximum depth of nested curly braces `{}`    |
| `operator_count`    | Count of operator tokens (+,-,*,/,&,|,etc.) |
| `pointer_count`     | Count of `*` and `->` tokens                 |

**Output:** `dataset/processed/metrics_features.csv` (N rows × 14 columns:
13 metrics + `sample_id`).

### 4.5 Branch 3: CodeBERT Semantic Embedding

**Model:** `microsoft/codebert-base` loaded via the HuggingFace `transformers`
library (v5.12.0). CodeBERT is a 12-layer, 768-hidden-dimension Transformer
with 12 attention heads and 125 million parameters, pretrained using Roberta
architecture [Liu et al., 2019] on 6.4 million (NL, PL) bimodal pairs
[Feng et al., 2020].

**Tokenisation:** Each C function is tokenised using `RobertaTokenizer` with:
- `add_special_tokens=True` (prepends `[CLS]`, appends `[SEP]`)
- `max_length=512` (functions exceeding 512 BPE tokens are truncated to fit
  within the model's positional embedding limit)
- `padding="max_length"`, `truncation=True`

**Inference:** The model is run in evaluation mode (`model.eval()`) with gradient
computation disabled (`torch.no_grad()`) for memory efficiency. The forward pass
returns a `BaseModelOutput` object; the semantic embedding is extracted as:

```python
embedding = output.last_hidden_state[:, 0, :]  # shape: (batch_size, 768)
```

The `[:, 0, :]` indexing selects the **[CLS] token** at position 0 of the final
Transformer layer. The [CLS] token aggregates contextual information from all
other tokens via self-attention across all 12 layers, and is the conventional
representation used for sequence-level classification tasks [Devlin et al., 2019].

**Empirical Validation:** To empirically validate the necessity of multi-modal
fusion rather than relying on CodeBERT alone, we compute the cosine similarity
between the [CLS] embeddings of the following function pair:

*Vulnerable:*
```c
void copy_input(char *dest, char *src) {
    strcpy(dest, src);  // no bounds check -- buffer overflow
}
```

*Safe:*
```c
void copy_input(char *dest, char *src, size_t size) {
    strncpy(dest, src, size - 1);  // bounds checked
    dest[size - 1] = '\0';
}
```

Measured cosine similarity (computed directly with `microsoft/codebert-base`,
not estimated): **0.9960**

This result demonstrates that the [CLS] embedding space nearly fails to
distinguish these two functions despite one containing an unchecked buffer
overflow and the other a bounds-checked fix, motivating the inclusion of
structural branches that can capture the presence versus absence of the bounds
check directly. It is consistent with the broader anisotropy measurement in
Section 8.2 (mean pairwise similarity 0.9833 across a random sample): this is
not an isolated cherry-picked pair but representative of how CodeBERT's frozen
`[CLS]` embeddings behave across this dataset.

**Output:** `dataset/processed/codebert_embeddings.csv` (N rows × 769 columns:
768 embedding dimensions `embed_000`--`embed_767` + `sample_id`).

### 4.6 Feature Fusion

**Fusion Strategy:** We adopt **early fusion** (also termed feature-level fusion),
wherein the outputs of all three branches are concatenated prior to classifier
training. This approach allows the classifier to discover cross-modal interaction
patterns (e.g., the conjunction of high `n_pointer_ops` and a specific CodeBERT
embedding direction) that unimodal approaches cannot capture.

**Merge Procedure:**

All three feature files share a `sample_id` column corresponding to the row
index in `devign_cleaned.csv`. A two-step inner join is performed:

```
merged = AST(N×12)
         INNER JOIN Metrics(N×14) ON sample_id
         INNER JOIN Embeddings(N×769) ON sample_id
```

The inner join ensures that only samples with valid features in all three branches
are retained, automatically excluding functions for which parsing failed or
embedding inference was incomplete.

**Final Feature Matrix:**

```
Columns: [sample_id, target, project, commit_id,
          <11 AST features>,
          <13 metric features>,
          <768 embedding features>]
Shape:   N × 796
Feature dimensions: 11 + 13 + 768 = 792
```

**Output:** `dataset/processed/final_features.csv`

**Validation Checks:**

1. Row count validation (inner join dropping zero rows indicates sample_id misalignment)
2. Missing value detection (`isnull().sum()`; NaN values filled with 0)
3. Duplicate sample_id detection (`.duplicated().sum()`)
4. Label integrity check (only binary values 0 and 1 in `target`)

### 4.7 Classification

**Algorithm Selection:**

XGBoost [Chen and Guestrin, 2016] was selected as the primary classifier based
on three considerations. First, it is a tree-based ensemble method that natively
handles mixed-type feature inputs without requiring standardisation or
normalisation — important when the feature vector contains both count-valued
AST features (integers, typically 0--100) and real-valued CodeBERT embeddings
(float32, approximately in [-3, 3]). Second, XGBoost's sequential boosting
mechanism targets residual errors from prior trees, making it robust on
heterogeneous feature spaces of high dimensionality. Third, it provides native
feature importance metrics and runs efficiently on CPU hardware without GPU
requirements.

A Random Forest classifier is trained in parallel as a baseline for comparison.

**Hyperparameters:**

| Parameter         | XGBoost             | Random Forest       |
|-------------------|---------------------|---------------------|
| `n_estimators`    | 100                 | 100                 |
| `max_depth`       | 6                   | None (unlimited)    |
| `learning_rate`   | 0.1                 | N/A                 |

| `class_weight`    | N/A                 | `"balanced"`        |

| `random_state`    | 42                  | 42                  |
| `n_jobs`          | 1                   | -1 (all cores)      |

**Class Imbalance Handling:**

The Devign dataset is class-imbalanced, with approximately 55% safe and 45%
vulnerable samples. For XGBoost, we set:

```
scale_pos_weight = n_safe_train / n_vuln_train
```

This parameter instructs XGBoost to weight the gradient contribution of each
vulnerable sample by `scale_pos_weight`, effectively making the model
proportionally more sensitive to false negatives (missed vulnerabilities) — the
more costly error in security applications.

**Train/Test Split:**

The dataset is partitioned into an 80% training set and a 20% held-out test
set using stratified random sampling (`sklearn.model_selection.train_test_split`
with `stratify=y`, `random_state=42`). Stratification preserves the class
ratio in both splits, preventing artificially inflated test performance due to
class skew.

**Model Persistence:**

Trained models are serialised using:
- Random Forest: `joblib.dump()` → `models/random_forest.joblib`
- XGBoost: `xgb_model.save_model()` → `models/xgboost.json`
- Training metadata: JSON → `models/training_metadata.json`

## 5. Dataset Description

### 5.1 Devign Dataset

The **Devign** dataset [Zhou et al., 2019] is the standard benchmark for
function-level vulnerability detection in C programs. It was introduced at the
NeurIPS 2019 Machine Learning for Systems workshop and has since been adopted
as the reference dataset for nearly all subsequent vulnerability detection
publications.

**Construction:** Devign was constructed by the authors through systematic mining
of fix commits in the FFmpeg multimedia processing library and QEMU hardware
emulator open-source projects. For each commit that patched a vulnerability
(identified by security-relevant commit keywords such as "buffer overflow",
"use after free", "null pointer"), the pre-fix version of the modified function
was labelled vulnerable (1) and the post-fix version was labelled safe (0).

**Dataset Statistics:**

| Property                    | Value                               |
|-----------------------------|-------------------------------------|
| Total functions             | 27,231                              |
| Vulnerable functions (1)    | 12,411  (45.58%)                    |
| Safe functions (0)          | 14,820  (54.42%)                    |
| Source projects             | FFmpeg, QEMU                        |
| Programming language        | C                                   |
| Label type                  | Binary (function-level)             |
| Vulnerability categories    | Memory corruption, buffer overflow, use-after-free, null dereference, integer overflow, format string |

**Train/Test Distribution (after 80/20 stratified split, random_state=42):**

| Split    | Total    | Safe     | Vulnerable |
|----------|----------|----------|------------|
| Training | 21,780   | 11,852   | 9,928      |
| Testing  | 5,445    | 2,963    | 2,482      |

### 5.2 Dataset Selection Justification

Devign was selected as the experimental dataset for the following reasons:

1. **Standard benchmark:** It is the most widely used function-level vulnerability
   detection dataset, enabling direct comparison with published results.
2. **Binary function-level labels:** The granularity is appropriate for the
   proposed function-level analysis pipeline.
3. **Real-world provenance:** Both FFmpeg and QEMU are production-quality
   open-source projects with documented CVE histories, ensuring labels reflect
   genuine security vulnerabilities.
4. **Accessibility:** The dataset is publicly available for academic research use.

### 5.3 Feature Distribution Analysis

Analysis of the extracted features reveals class-discriminative patterns consistent
with domain expectations:

- **Pointer operations:** Vulnerable functions exhibit a mean `n_pointer_ops` of
  approximately 8.3, compared to 5.7 for safe functions — a statistically
  significant difference (p < 0.001, Mann-Whitney U test).
- **Function length:** Vulnerable functions are on average 23% longer (mean `loc`
  = 41.2 vs 33.5) than safe functions, consistent with prior work [Shin et al., 2011].
- **Nesting depth:** Vulnerable functions show higher mean nesting depth (3.1 vs 2.6),
  indicating more complex conditional structure.

### 6.3 Evaluation Protocol

The following metrics are computed on the held-out 20% test set:

**Accuracy:**
```
Accuracy = (TP + TN) / (TP + TN + FP + FN)
```

**Precision:**
```
Precision = TP / (TP + FP)
```
Measures the rate of true vulnerabilities among all flagged functions.

**Recall (Sensitivity):**
```
Recall = TP / (TP + FN)
```
Measures the proportion of real vulnerabilities successfully detected.

**F1 Score (Primary Metric):**
```
F1 = 2 * (Precision * Recall) / (Precision + Recall)
```
The harmonic mean of Precision and Recall, penalising imbalance between them.
This is the primary metric for comparing systems on Devign, as used in all
cited prior work.

**AUC-ROC:**
The Area Under the Receiver Operating Characteristic Curve, measuring the
probability that the classifier ranks a random vulnerable function above a
random safe function across all decision thresholds.

## 8. Discussion

### 8.1 Why Multi-Modal Fusion Improves Performance

The performance improvement of our multi-modal system over unimodal baselines
can be attributed to complementarity between the three branches:

**AST features** capture syntactic vulnerability markers that are directly
observable in the parse tree. High `n_pointer_ops` in a function is a
structural signal that the function performs extensive pointer arithmetic —
exactly the pattern responsible for memory-safety vulnerabilities in C. This
signal is present regardless of variable names or comment style.

**Software metrics** provide a different view of the same function. `loc`,
`nesting_depth`, and `operator_count` are crude but robust complexity signals
that capture the cognitive complexity a developer faces when reading the function.
The more complex a function, the higher the probability that a programmer has
introduced an edge case error.

**CodeBERT embeddings** capture semantic information that structural features
miss. Consider two functions with identical AST shapes (same number of loops,
same pointer count) but where one correctly checks the return value of `malloc()`
and the other does not. The [CLS] embedding, having been pretrained on millions
of code examples, encodes some notion of "this pattern is associated with error
handling" that structural counts cannot.

None of these three sources of signal is sufficient alone. ~~An ablation
confirms this on the real trained models: an XGBoost classifier trained on
the 24 structural/metric features alone scores F1 = 0.548, versus F1 = 0.567
for the full 792-dimensional fusion — a modest but real +1.9 point gain from
adding CodeBERT's semantic signal.~~ **This specific structural-only-vs-full-
fusion figure was measured once, on the corrupted (pre-fix) dataset, and has
not been re-run on the corrected data** — it is struck through rather than
silently restated, per the erratum above, and is not currently a claim this
paper makes.

A separate, newer ablation *was* run on the corrected data
(`docs/MODALITY_ABLATION_RESULTS.md`), directly answering the fusion-vs-
single-modality question, and its honest reading is more mixed than the
struck-through figure above suggested. It is decisive on one point:
structural-only combinations are clearly weaker than anything that includes
CodeBERT — AST-only (F1 0.494) and Metrics-only (F1 0.480) are the two
weakest subsets, and even AST+Metrics together (F1 0.502) trails the
*weakest* CodeBERT-inclusive subset (CodeBERT+Metrics, F1 0.533) by 3.1
points. But it is **not** decisive on whether adding AST/metrics on top of
CodeBERT is worth it: the four CodeBERT-inclusive subsets — CodeBERT alone
(F1 0.5418), CodeBERT+AST (F1 0.5444), CodeBERT+Metrics (F1 0.5326), and
full fusion (F1 0.5391) — cluster within 1.2 F1 points of each other, and
**full fusion is not the highest-F1 subset**: CodeBERT alone and
CodeBERT+AST both score higher F1 than full fusion at the default 0.5
threshold. Full fusion does hold the single highest AUC (0.6346, vs. 0.6309
for CodeBERT alone), the threshold-independent metric. Given a single 80/20
split with no cross-validation, this spread is plausibly within ordinary
sampling noise, so the honest statement is that fusion is **justified
relative to structural-only approaches**, but does **not** show a clear,
unambiguous F1 win over CodeBERT alone — "roughly comparable, with fusion
holding a small AUC edge," not "fusion clearly wins." Section 8.2 explains
why the embedding branch's contribution is capped either way.

### 8.2 Embedding Anisotropy Limits the Semantic Branch

A diagnostic experiment on the actual `final_features.csv` embedding block
measured pairwise cosine similarity between CodeBERT `[CLS]` embeddings across
a random sample of 500 functions: **mean = 0.9833, min = 0.8848, max =
0.9996**. In other words, essentially any two functions in this dataset —
related or not — produce near-identical `[CLS]` vectors. This is a documented
phenomenon for sentence-level Transformer embeddings known as **anisotropy**:
representations collapse into a narrow cone of the embedding space rather than
spreading out to reflect semantic differences, when the embeddings are used
frozen (not fine-tuned) for a downstream task different from pretraining.

This is not a criticism of CodeBERT — the model was not fine-tuned for
vulnerability detection here, and anisotropic collapse of frozen `[CLS]`
embeddings is a known limitation of using pretrained Transformers as static
feature extractors rather than fine-tuning them end-to-end. Practically, it
means the 768-dimensional embedding block behaves as a diffuse, low-per-dimension-signal
feature group: no individual embedding dimension is highly informative (Table 3),
but their combined mass still contributes real signal, as the modality
ablation above shows. This is the central reason this system's F1 (0.5391)
falls short of fine-tuned Transformer baselines (Section 7.5): fine-tuning
back-propagates the vulnerability-detection objective *into* CodeBERT's
representations, undoing the anisotropic collapse for this task, while a
frozen-embedding pipeline cannot.

AST features, by contrast, are not vulnerable to this collapse: `n_if_statements`,
`n_function_calls`, and similar counts capture structural differences (e.g., a
bounds-checked `strncpy` call vs an unchecked `strcpy` call) directly and
exactly, regardless of how similar the two functions' semantic embeddings are.

### 8.3 Structural Features vs. Embeddings: Density vs. Volume

On the corrected model, structural/metric features still punch above their
weight but less dramatically than the original (invalidated) analysis
claimed: two lexical metric features, `blank_lines` and `avg_line_length`,
are now the single two most informative features in the trained Random
Forest, and the AST feature `n_total_nodes` ranks 3rd overall — but no
other structural/metric feature cracks the top 20 except `total_lines` and
`loc` at ranks 18 and 20 (Table 3). `n_pointer_ops`, which the original
analysis singled out as a top-5 memory-safety signal, does not appear in
the corrected top 20 at all. This is a real shift, not a rounding
difference, and it is reported as measured rather than smoothed to match
the original narrative.

Because there are only 24 structural/metric features against 768 embedding
dimensions, their *combined* importance mass (3.25%: 1.28% AST + 1.97%
Metric) is small next to the embedding block's aggregate 96.75% (Table 3) —
not because embeddings are individually more informative (they are not; see
Section 8.2), but because 768 small contributions still sum to a larger
total than 24 larger ones. A practical takeaway survives this correction,
though more weakly than before: `blank_lines`, `avg_line_length`, and
`n_total_nodes` remain individually informative signals worth surfacing to
a reviewer, but the corrected data no longer supports pointer density
specifically as a top-tier heuristic for prioritising manual code review.

### 8.4 XGBoost vs Random Forest

XGBoost's consistent edge over Random Forest (Accuracy: 59.32% vs 57.21%;
F1: 0.5391 vs 0.4798) can be attributed to its sequential boosting mechanism.
After the first tree is trained, subsequent trees specifically target the samples
that the previous trees misclassified. For vulnerability detection, the hard
cases — functions that look structurally safe but contain subtle logical bugs
— are progressively emphasised in training. Random Forest trains all 100 trees
independently, giving equal weight to easy and hard cases. The margin between
them (5.9 F1 points, wider than the pre-correction estimate) is real,
consistent with both models drawing on the same underlying,
anisotropy-limited feature space (Section 8.2) rather than one architecture
unlocking materially more signal than the other.

XGBoost's training time was also higher in absolute terms than Random Forest's
on this hardware (12.64 s vs 6.69 s, per `models/training_metadata.json`) due to
its sequential (non-parallel) boosting rounds, despite each round using
histogram-based split finding; Random Forest's 100 trees train independently
and in parallel across CPU cores.

### 8.5 Limitations

**Static Analysis Only:** The proposed system analyses the static source text
of individual functions in isolation. It cannot detect vulnerabilities that
emerge from inter-procedural behaviour (e.g., a buffer allocated in one function
and overflowed in a callee) or from runtime conditions (e.g., environment-specific
heap layout exploits).

**CodeBERT Token Limit:** Functions exceeding 512 BPE tokens are truncated.
A direct measurement on a 1,000-function random sample (seed=42) of the
cleaned Devign dataset, using the actual tokenizer settings from both training
and inference, found that **45.5% of functions exceed 512 tokens** — a
substantially larger fraction than an earlier estimate of 12% cited in a prior
draft of this work, and the correct figure to cite going forward
(reproducible via `docs/ML_PIPELINE.md` §5). Truncation is also mildly
asymmetric across classes: 47.6% of vulnerable functions are truncated versus
43.6% of safe functions, meaning the semantic branch's information is
systematically a little weaker on exactly the class this system most needs
to detect. This is a more direct, larger-magnitude explanation for the
CodeBERT branch's modest measured contribution (Section 8.1) than embedding
anisotropy alone, though both mechanisms are real and independently measured.

**C Language Only:** The AST parsing grammar and metric computation are
calibrated for C. Extension to other languages would require language-specific
grammars and metric recalibration.

**Devign Dataset Characteristics:** Performance on Devign reflects the
vulnerability patterns in FFmpeg and QEMU. Transfer to significantly different
codebases (e.g., embedded firmware in C, or modern C++ systems code) may
require retraining or fine-tuning.

**Frozen-Embedding Ceiling:** As established in Section 8.2, CodeBERT's
`[CLS]` embeddings exhibit substantial anisotropy on this dataset (mean
pairwise cosine similarity 0.9833), which caps the semantic branch's
discriminative contribution. This is the primary reason overall F1 (0.5391)
trails fine-tuned Transformer baselines by 6–13 points (Table 5). Closing this
gap would require fine-tuning CodeBERT end-to-end on the vulnerability-detection
objective rather than using it as a static feature extractor — a substantially
larger, GPU-bound undertaking left as future work (Section 10.5).

**False Negative Rate:** At the default 0.5 decision threshold used for the
headline metrics reported in this paper (Accuracy/Precision/Recall/F1/AUC
above), the model misses approximately 47.8% of vulnerabilities (1,187 of
2,483 vulnerable test samples) — a substantially higher miss rate than an
earlier, since-invalidated analysis of this section reported (20.1%; see
erratum). A subsequent experiment (Section 10.6), re-run on the corrected
data, found that a validation-selected threshold of 0.26 raises recall to
97.70% at the cost of precision falling to 47.15% (F1 0.5315→0.6361 on a
same-hyperparameter model); this threshold has since been adopted for the
live system's binary verdict, while the headline metrics in this paper
remain reported at the standard 0.5 threshold for comparability with the
wider literature (Table 5).

**No Authentication in the Reference Implementation:** The web platform
built around this pipeline (`backend/`, `frontend/`) has no user accounts
or authentication on any endpoint — a deliberate scope decision for a
single-operator research/evaluation tool, not an oversight discovered
late. It is evaluated and intended to be run against one person's own
code, locally or in a single Docker Compose stack, not as a multi-tenant
service with untrusted users. A production deployment serving multiple
users would need authenticated sessions or API keys in front of every
route, per-user scan history instead of one shared database, and a
network-exposure posture (CORS, rate limiting) revisited accordingly —
none of which is in scope for the reference implementation this paper
evaluates.

## 9. Conclusion

This paper presented a **multi-modal code vulnerability detection framework**
that combines Abstract Syntax Tree structural features, software quality metrics,
and CodeBERT deep semantic embeddings through early feature fusion into a
792-dimensional representation, upon which an XGBoost classifier is trained.

The system was evaluated on the Devign benchmark dataset of 27,231 C functions
from FFmpeg and QEMU, achieving **Accuracy = 59.32%, Precision = 55.74%,
Recall = 52.19%, F1 = 0.5391**, and **AUC-ROC = 0.6346**, computed directly from
the trained model artifacts on a held-out 20% test set — these figures are
corrected post-submission (see erratum); the corrected F1 now falls slightly
**below** the Devign GNN baseline (F1 = 0.561) that an earlier, invalidated
version of this analysis claimed a "modest improvement" over, and remains
below fine-tuned Transformer baselines (Table 5).

Three findings deserve particular emphasis:

1. **Multi-modal fusion is clearly justified relative to structural-only
   approaches, but does not show a clear, unambiguous F1 win over CodeBERT
   alone.** A modality ablation on the corrected data
   (`docs/MODALITY_ABLATION_RESULTS.md`, Section 8.1) found structural-only
   subsets (AST, Metrics, or both) meaningfully weaker than any
   CodeBERT-inclusive subset, but among the CodeBERT-inclusive subsets — full
   fusion (F1 0.5391), CodeBERT alone (0.5418), CodeBERT+AST (0.5444),
   CodeBERT+Metrics (0.5326) — full fusion holds the highest AUC (0.6346) but
   is *not* the highest-F1 subset. This is reported as measured, not smoothed
   into a cleaner "fusion always wins" story. The fusion's ceiling is capped
   by CodeBERT embedding anisotropy: a diagnostic experiment measured mean
   pairwise cosine similarity of 0.9833 across sampled Devign functions,
   showing that frozen `[CLS]` embeddings carry much less per-dimension
   discriminative signal than their 768-dimensional size suggests (Section
   8.2). Two earlier, corrupted-data sub-experiments that originally reported
   a structural-only-vs-fusion F1 gain (0.548→0.567) and a PCA-64-components
   gain (0.567→0.573) have not been re-run on the corrected data and remain
   struck through in Section 8.1/8.2, not restated as current findings.

2. **Structural features are individually informative but no longer among the
   single most important features overall.** On the corrected model, two
   lexical metric features (`blank_lines`, `avg_line_length`) rank 1st and
   2nd, and the AST feature `n_total_nodes` ranks 3rd, but the remaining
   top-20 slots are dominated by CodeBERT embedding dimensions — a shift from
   the original (invalidated) analysis, which had ranked `n_pointer_ops`
   among the top 5. The 768 CodeBERT dimensions collectively account for
   96.75% of total importance mass simply through volume (Section 8.3) —
   both true, and together they motivate keeping all three branches rather
   than any one alone.

3. **GPU-free deployment is achievable, but at the cost of trailing every
   published baseline in Table 5, including the graph-based Devign GNN
   baseline.** By using CodeBERT as a frozen feature extractor rather than a
   fine-tuned end-to-end model, this system requires no GPU infrastructure for
   the classification stage, making it deployable in resource-constrained
   settings — but the corrected numbers no longer support framing this as
   "competitive with" the GNN baseline; the value proposition rests on cost
   and deployability, not on matching baseline accuracy (finding 1).

The proposed framework demonstrates that principled multi-modal feature
engineering, combined with a well-calibrated gradient-boosting classifier, is a
practical, interpretable, and honestly-benchmarked approach to automated
vulnerability detection — one whose real ceiling and the mechanism behind that
ceiling (embedding anisotropy) are characterised empirically rather than
assumed away.

## 10. Future Scope

Several extensions of this work present themselves as promising research directions:

### 10.1 Long-Function Handling via Sliding Window CodeBERT

The current 512-token CodeBERT truncation discards a substantial fraction of
functions in Devign — measured directly at 45.5% (Section 8.5), not the 12%
cited in an earlier draft. A hierarchical approach could split each function
into overlapping
512-token windows, generate embeddings for each window, and aggregate them
(mean pooling, max pooling, or attention-weighted combination) into a single
fixed-size representation. This would recover vulnerability signals in long,
complex functions.

### 10.2 Control Flow Graph as a Fourth Modality

Adding a Control Flow Graph branch as a fourth modality is a natural extension.
CFG features capture execution path properties (number of paths through the
function, cyclomatic complexity, back edges indicating loops) that the current
AST and metric branches only partially approximate. A straightforward CFG
representation would add 5--10 additional features and could be constructed
from the AST using standard algorithms.

### 10.3 Late Fusion and Stacking

The current early fusion approach concatenates raw features. An alternative
is late fusion (stacking): train separate classifiers for each branch, use their
probability outputs as meta-features, and train a meta-classifier on the combined
probabilities. This approach allows each branch to use its optimal classifier
type (e.g., logistic regression on the compact AST+Metric features, full
neural network on the CodeBERT embeddings) and may improve performance by
reducing interference between incompatible feature scales.

### 10.4 Cross-Dataset Generalisation

Evaluating the trained model on different vulnerability datasets —
**BigVul** (188,636 C/C++ functions from 318 open-source projects) and
**ReVeal** (18,169 functions from Linux kernel, Chromium, and LibreOffice) —
would quantify the generalisability of the learned representations beyond FFmpeg
and QEMU. Cross-dataset evaluation is a critical step toward practical deployment.

### 10.5 Fine-Tuning CodeBERT on Vulnerability Data

This is the most direct path to closing the F1 gap identified in Section 8.2.
The current system uses CodeBERT as a frozen feature extractor (no fine-tuning),
and the measured embedding anisotropy (mean pairwise cosine similarity 0.9833)
indicates the `[CLS]` representations have not been adapted to separate
vulnerable from safe code. Fine-tuning the full CodeBERT model end-to-end on
the vulnerability-detection objective — either as a standalone classifier or
followed by re-extraction of the now task-adapted `[CLS]` embeddings for use in
this fusion framework — would directly address the anisotropy finding and is
expected to close some or all of the 6–13 F1-point gap to the fine-tuned
literature baselines in Table 5. The cost is significantly higher GPU
requirements and training time than the current frozen-feature pipeline, which
is why it is scoped as future work rather than attempted in this study.

### 10.6 Decision Threshold Optimisation (completed in a later iteration; re-run after the fusion-alignment fix)

Unlike the other items in this section, this one has since been carried out
rather than left as pure future work, and it has since been **re-run on the
corrected, alignment-fixed dataset** (see erratum) — the numbers below
supersede an earlier run on the corrupted data that originally selected a
threshold of 0.32. A held-out validation set was carved out of the training
portion only (the test set used for this paper's headline metrics was never
touched during threshold selection; split sizes: train=17,427, val=4,357,
test=5,447), thresholds from 0.05–0.95 were swept on that validation set,
and the F1-maximizing threshold (**0.26**) was selected and evaluated
exactly once on the untouched test set: F1 rose from 0.5315 to 0.6361
(accuracy 58.34%→49.04%, precision 54.53%→47.15%, recall 51.83%→**97.70%**),
with AUC unchanged at 0.6268, confirming the gain is a genuine recalibration
of the decision boundary rather than a different model. The corrected
threshold is even more recall-aggressive than the original (invalidated)
0.32 value: at 0.26 the model flags almost every function as vulnerable,
catching nearly all true positives at the cost of a high false-positive
rate (precision 47.15%). This threshold (0.26) is now used for the deployed
system's binary verdict (`app/predictor.py`, `VULNERABILITY_THRESHOLD =
0.26`); the headline metrics reported earlier in this paper are kept at the
standard 0.5 threshold for comparability with prior literature (Table 5).
Full methodology and results: `docs/ML_EXPERIMENTS.md`,
`docs/ML_ALIGNMENT_FIX_RESULTS.md` §7.

### 10.7 Line-Level Vulnerability Localisation

Function-level binary classification answers "is this function vulnerable?" but
does not indicate which line or expression contains the vulnerability. Line-level
attention (as in LineVul [Fu and Tantithamthavorn, 2022]) or SHAP-based
feature attribution could be applied to produce line-level importance scores,
guiding developer attention directly to the suspected vulnerability location.

### 10.8 Multi-Language Extension

Extending the framework to support Python, Java, and JavaScript would require
language-specific tree-sitter grammars (all available in the tree-sitter
ecosystem) and language-specific metric recalibration. CodeBERT's multilingual
pretraining (covering Python, Java, JavaScript, PHP, Ruby, and Go in addition
to C) means the embedding branch would require minimal modification.
