## 4. Real, measured data-quality facts relevant to the upcoming Phase 4 audit

- **Original raw dataset:** 27,318 samples (`dataset/notes/data_quality_report.md`,
  auto-generated by `preprocess_dataset.py`, not hand-written).
- **Exact-duplicate code strings removed:** 60 (0.22% of raw data) — real,
  measured, already handled by `drop_duplicates(subset=["func"])`.
- **Just-measured (this audit), whitespace-normalized near-duplicate check**
  on `dataset/processed/devign_cleaned.csv` (stripping all whitespace before
  hashing, to catch near-duplicates the exact-string dedup step would miss):
  **30 near-duplicate groups found (≈0.11% of the cleaned dataset)** — a small
  number, so this is not a dominant leakage source for the dataset as a whole.
  However: **26 of those 30 groups have inconsistent labels** — i.e., the same
  code (modulo whitespace) is labeled vulnerable in one row and safe in
  another. Manually inspected two such groups directly: both are genuine
  before/after–style pairs from FFmpeg where the non-whitespace content is
  identical but the raw character length differs (16–41 chars, consistent
  with reformatting, not a real logic change) and the label disagrees. This
  is real, measured evidence of **label noise inherited from Devign's
  commit-based automatic labeling**, not a bug in this project's own
  pipeline — but it is a legitimate, citable limitation to document rather
  than paper over, and it directly informs Phase 4's data-leakage /
  label-quality investigation.
- **No grouped/project-aware train/test split exists today** — since the
  split is a plain random stratified split (not grouped by `project` or
  `commit_id`), and since Devign is known in the wider vulnerability-detection
  literature for exactly this kind of near-duplicate-across-splits concern,
  this is the single highest-priority item for the Phase 4 forensic audit:
  quantify how many near-duplicate-content samples (if any) actually land on
  opposite sides of the current train/test split, not just present anywhere
  in the dataset.

## 6. GitHub scanner (current state, to be improved in Phase 9)

- `backend/github_service.py`: clone depth 50, single-branch, `MAX_REPO_FILES=200`,
  `MAX_FILE_SIZE=512KB`, 90s clone timeout. Already reports (since last
  session's work) `files_detected`/`files_analyzed`/`files_skipped` and
  persists `repo_url`/`repo_name`/`branch`/`commit_sha` per batch in a new
  `github_batch_meta` table — this table is **SonarQube-independent** (it is
  general GitHub-scan provenance, needed regardless of any external tool) and
  will be **kept**, not removed, in Phase 1.
- No cancellation, no progress streaming, no caching of repeated scans of the
  same repo/commit — real gaps, to be addressed in Phase 9/10.

## 7. Known limitations (carried into this pass, not newly discovered)

- Modest classifier accuracy (F1 ≈ 0.567), reported honestly in
  `paper/research_paper.md`.
- CodeBERT embeddings are frozen (not fine-tuned) and measurably anisotropic.
- No CWE/rule-level classification produced by this platform.
- 200-file cap per GitHub scan.
- No SonarQube API integration (by design, and now explicitly required to
  stay that way per the current instructions).

be removed, since the user now wants a manual, two-browser-tab comparison
workflow instead of anything embedded in the product. This baseline report
records their existence and purpose before removal so the removal is
auditable.
